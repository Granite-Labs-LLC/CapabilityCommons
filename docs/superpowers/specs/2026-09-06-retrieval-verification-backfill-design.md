## Problem

Two separate doubts about the current retrieval quality signal surfaced during the 2026-09-06 reconciliation, and both need resolving before anyone trusts an eval score enough to act on it:

### 1. The 2026-05-14 eval report may already be stale

`eval/reports/2026-05-14-smoke.md` lists four intent-classifier misses (S4 in the follow-ups doc). Re-checking `src/capability_commons/retrieval/intent.py` against those four queries this session:

| Query | Report says | Current code says |
|---|---|---|
| "Renter-safe food resilience" | miss (got `how_to`) | matches `LOCALIZE` via `\brenter\b` — correct |
| "Is bleach safe for treating drinking water?" | miss (got `how_to`) | matches `SAFETY_CHECK` via `\b(?:is\|are) .* safe\b` — correct |
| "Why is my rain barrel system not flowing?" | miss (got `how_to`) | matches `DEBUG_FAILURE` via `why is(?: my)? .* (?:not\|broken)` — correct |
| "What is the gold-goats-guns portfolio about?" | miss (expected `why`) | still doesn't match anything — genuinely still open |

Three of four "known misses" already have passing regex logic and unit test coverage in `tests/test_retrieval_intent.py`. Either the smoke report was generated against a build that predates these fixes, or something else prevents the fix from taking effect at runtime (a stale deployed process, an import ordering issue, caching). This needs an actual re-run against a live server, not another code read.

### 2. Seed objects may have never been embedded

`cli/seed.py`'s `seed_graph()` does emit `OutboxEvent(event_type="version.published", ...)`, so in principle the 49 seed objects get segmented and embedded exactly like ingested content, via the outbox worker. But timeline evidence suggests otherwise:

- The 38-ticket backlog's Phase 0 seed load likely happened before or around when embedding indexing (Phase 1, `EmbeddingService`) was wired in.
- `search_hybrid`'s reciprocal rank fusion unions FTS candidates with vector candidates. An object with **no** embedding is simply absent from the vector list — it can still surface via FTS, but it loses the RRF contribution a properly-embedded object gets "for free."
- Every eval query in the 2026-05-14 report returned GGG-corpus objects at the top, even for queries like "I need drinking water if the power is out" where `water.safe-storage` is a real, already-published seed object that should be a strong FTS match on "water."

This is a hypothesis, not a confirmed finding — nobody has queried `content_segments`/`context_object_versions` in a live database this session to check whether seed-object rows have `NULL` embeddings. It needs to be checked directly, and if true, fixed with a backfill, before drawing any conclusion from an eval run (including the one in the paired ingestion plan).

## Scope

1. **Re-run the eval harness** against a live server on current `main` and diff against the 2026-05-14 report, per-query. Update or retire the followups doc's S4 section based on what actually happens now — don't leave a stale "known issue" sitting in the docs once it's confirmed fixed.
2. **Check embedding NULL-ness** for existing seed objects: a one-off query against `content_segments` (or `context_object_versions` joined to whatever holds the vector column) grouped by whether the object came from the seed pack vs. an ingest project.
3. **Build the embedding backfill job** (already an explicit TODO Tier 3 item) if the hypothesis confirms: a CLI command that re-emits `version.published`-equivalent events (or calls the embedding path directly) for every published object whose segments lack a vector, idempotently.
4. **Wire query caching** (TODO Tier 2: LRU on `(normalized_query, intent, context_hash)`) — bundled here because it touches the same retrieval hot path and is small once the above is settled.
5. **Finish `language_code` wiring** (MULTI-1 scaffold exists but doesn't affect ranking/synthesis) — the Spanish gold query (`¿Cómo almaceno agua potable durante un apagón?`) is a real regression test for this; it should keep failing loudly with "no matching results" until Spanish content or cross-lingual matching actually lands, per the gold file's own comment, so the target here is not "make it pass" but "confirm it still fails for the right reason" plus scope out what full wiring would take.

## Non-goals

- This is not a redesign of the intent classifier or the ranking algorithm. If the 4th S4 case ("what is X about" → `why`) is still broken after re-verification, fix the regex; don't rearchitect.
- Not building actual Spanish-language content or translation — that's TODO Tier 3 ("Translation workflow").

## Success criteria

- A fresh, dated eval report exists that the team can trust without re-reading source code first.
- A documented, verified answer (not a hypothesis) to "do seed objects have embeddings," with a backfill run if the answer is no.
- Query caching lands with a cache-hit test and a note on invalidation (cache keys should probably include an object-publish-version marker so a re-publish doesn't serve stale cached answers indefinitely).

## What actually happened (2026-09-06 execution against the real dev database)

The original hypothesis above — "seed objects were loaded before embedding indexing existed and never got backfilled" — was **wrong in its specifics but right that something was structurally broken.** Found by restarting `capabilitycommons-db-1` (a stopped container with its original data volume, 4 months old) and querying it directly rather than reasoning from code alone:

1. **The seed pack had never been loaded into this database at all.** Only the 34 `ggg-2026-03` objects existed. `water.safe-storage` and every other seed slug simply didn't exist as rows — that's why they never surfaced in search, independent of embeddings or ranking. **Fixed**: loaded both seed packs (`expanded_seed/`, 25 objects; `capability_commons_module_seed_pack_v1/`, 24 objects) — 49 objects now present.
2. **Found and fixed a real bug in `cli/seed.py`'s edge loader**: when loading a second seed pack whose `edges.csv` references slugs from a *different, already-loaded* pack, the loader only checked its own in-memory slug map (built from the directory it's currently reading) and silently skipped the edge with a `WARN: missing edge node` — even though the target object existed in the database. Fixed by resolving any edge-referenced slug not in the in-memory map against the database before giving up on it. 48 previously-dropped `COVERS`/`EVALUATES` edges (module → capability object) now resolve correctly. Verified idempotent by re-running.
3. **Found and fixed a real reliability bug in `cli/worker.py`**: `_poll_batch()` set `event.processed_at` unconditionally, even when the handler raised an exception. Reproduced live: the `.env` file's `OPENAI_API_KEY` is currently **invalid** (401 `invalid_api_key` from OpenAI), so every `version.reindexed` event for the 49 newly-loaded objects failed to generate embeddings — and would have been marked permanently processed anyway, silently losing those embeddings forever with no retry path. This is almost certainly the real, general-purpose version of the original hypothesis: not "seed objects predate embedding indexing," but "any transient or configuration failure during indexing was permanent and unrecoverable by design." Fixed: a failed event now stays unprocessed (`processed_at` left `NULL`) so the next poll retries it once the underlying problem is fixed. Added a regression test (`tests/test_integration_embedding.py::test_worker_leaves_failed_event_unprocessed_for_retry`). The 51 stuck events from before the fix were manually reset to unprocessed so they're retry-eligible once a valid key exists — **no bespoke backfill script needed**; restarting the worker with a working key finishes the job.
4. **Blocking on**: a valid `OPENAI_API_KEY`. The one in `.env` returns 401. Someone needs to source a working key (from wherever the project's OpenAI billing/account actually lives — this isn't something to guess or regenerate blindly) before the 49 newly-loaded objects can be embedded and hybrid search can rank them properly. Until then, they're findable via FTS only.
5. **Re-ran the test suite** against this real database (`.venv` created fresh this session, base + dev deps only — see the disk-space note in the repo-hygiene checklist for why `[ingest]` extras aren't installed). 316 passed, 42 failed. Of the 42: ~34 share one root cause — a fresh `pip install` today pulls `fastapi==0.141.1`/`starlette==0.52.1`, and `prometheus-fastapi-instrumentator`'s routing internals break against that combination (`AttributeError: '_IncludedRouter' object has no attribute 'path'`) for every test that instantiates the FastAPI app. This is a new, real, previously-undocumented finding — `pyproject.toml`'s `fastapi>=0.115,<1.0` is too loose for what's actually compatible today. 2 more fail on the same invalid-API-key 401 (real integration tests exercising live embedding calls, correctly failing for a real reason). 1 (`test_publish_creates_outbox_event`) failed for a reason not yet diagnosed — not obviously related to anything changed this session. 1 (`test_ingest_parse`) needs the `[ingest]` extras that couldn't be installed.
6. Did **not** re-run the eval harness end to end (needs the API server up, which needs the FastAPI/prometheus pin issue above sorted first, or `METRICS_ENABLED=false` as a workaround) or resolve the intent-classifier S4 re-verification — those parts of this spec are still open.

### 2026-09-07, second follow-up: eval harness actually run — a third root cause found and fixed, two new ones surfaced

Started the API (`uvicorn`, port 8100) and worker for real against `capabilitycommons-db-1` (fixed a stale `.env` `DATABASE_URL` pointing at port 5433 — the container was recreated on 5435 during the Docker cleanup and `.env` was never updated; also cleared 331 more orphaned pending outbox events from this session's own test runs, same pre-existing test-residue issue as before). API started cleanly — the pin fix holds, no `_IncludedRouter` crash.

First eval run: **3/11, identical to the stale 2026-05-14 baseline**, despite the full backfill above. Investigated rather than accepting the number:

1. **Root cause: the entire 49-object seed pack had `lifecycle_state = 'draft'` in its own source CSVs and was never published.** `search/adapters/postgres_search.py` hard-filters both the FTS and vector queries to `ContextObject.lifecycle_state == PUBLISHED` (lines 116, 212) — a draft object is invisible to search no matter how well it's embedded. This is the real, final explanation for the original hypothesis in this doc's Problem section: not "objects predate embedding indexing" (wrong), not "objects don't exist" (fixed in the first follow-up), but "objects exist, are fully embedded, and are still filtered out by a lifecycle gate nobody had cleared."
2. **Fixed live, through the real publish path, not a bypass.** Wrote a one-off script calling `RegistryService.publish_version(obj.id, obj.current_version_id)` (no `bypass_gate`) for every non-GGG draft object. Result: **28/49 published** cleanly (re-indexed, re-embedded via the worker — confirmed `Processed 28/28 outbox events`, 0 pending after). **20/49 correctly blocked** by `validate_structured_data_or_raise`, not the editorial `PublishGate` — genuine Pydantic schema failures: 11 `skill_guide` objects (including `water.safe-storage`, the object most eval queries expect) missing `learning_objectives` and `teach_forward`; 9 `project_blueprint` objects missing `budget_notes`. The seed CSVs (`expanded_seed/imports/nodes.csv` etc.) were authored against an older shape of the schema and never updated when the schema gained these required fields. This is real, unwritten content (a `teach_forward` block needs a `three_minute_script`, `ten_minute_outline`, and `handout_points` — actual curriculum authorship), not something to fabricate blindly — flagged as a new TODO item rather than patched here.
3. **Re-ran eval after publishing: still 3/11, but every failure's shape changed.** Resilience-domain objects now dominate the top hits for every on-topic query — `water.treatment-selection`, `power.circuit-basics`, the water/power/food curriculum modules — confirming hybrid ranking works correctly once content exists, is embedded, *and* is published. Manually verified `water.safe-storage` is one of the 20 still-`draft` objects, not a ranking bug, when it didn't appear in the "I need drinking water" results.
4. **Two new, distinct, real gaps found underneath, both out of scope to fix here:**
   - Every resilience-domain answer now returns `citations: []` from `/v1/public/ask`, even though `implementation_plan[].source_slug` correctly cites the right objects. Traced to `services/evidence.py::list_citations_for_version` — `citations` is populated from `EvidenceSpan` rows explicitly linking a version to an `EvidenceSource`, a provenance concept distinct from "what was retrieved." GGG-corpus objects (real ingested documents) have these links; the hand-authored curriculum content has none. For safety-adjacent content (water treatment, food safety) this is a real editorial/trust gap, not an eval artifact — see TODO.
   - The gold file (`eval/gold/queries.yaml`) references slugs that don't exist anywhere in the actual seed pack under any name (`water.rain-barrel`, `power.starter-solar`, `water.chlorine-treatment`, `emergency-water-storage`, etc.) — it appears to have been written against a different or aspirational content plan than what the seed pack actually contains. Even a topically-correct retrieval result (e.g. `water.treatment-selection` for a bleach-safety query) can never pass against these `expects_any` lists. Needs either new content or a gold-file rewrite to match real seed slugs — a decision, not a bug fix.

Latest report: `eval/reports/2026-09-07.md`, superseding `2026-05-14-smoke.md`. All four scope items in this spec (re-run eval, check embedding NULL-ness, build backfill job, wire query caching/language_code) are now either done or superseded by more specific findings; query caching and `language_code` wiring remain genuinely un-started.

### 2026-09-07, third follow-up: fixed the 20 blocked objects — 3/11 → 5/11, found a fourth bug

Authored the missing `structured_data` fields directly from each object's own existing content (goal/steps_summary/failure_modes/performance_statement were already present and gave enough to work from): `learning_objectives` (4 each) + `teach_forward` (`three_minute_script`, `ten_minute_outline`, `handout_points`) for the 11 blocked `skill_guide` objects; `budget_notes` for the 9 blocked `project_blueprint` objects.

Tried `RegistryService.update_draft_version()` first (these are `lifecycle_state='draft'` objects, seemed like the obvious in-place-edit path) — it raised `ForbiddenError: Published current versions are immutable`. Root cause: the guard checks `obj.current_version_id == version.id`, not `lifecycle_state` — and `cli/seed.py`'s loader sets `current_version_id` on every seeded object unconditionally (see its "Set current_version_id and mark as published" block), regardless of what `lifecycle_state` the node's own CSV declared. So every seed object is "immutable" by this check even while still `draft` by `lifecycle_state` — a minor inconsistency in the seed loader, not fixed here (didn't block anything once routed around it). Fixed by using `create_version()` (copying all fields from the existing version, replacing only `structured_data`) + `publish_version()` on the new version instead — the correct path for these objects regardless.

Publishing the 9 `project_blueprint` objects surfaced a **fourth real bug**, more significant than the first three: `services/publish_gate.py`'s `SAFETY_BOUNDARY_REQUIRED_TYPES` includes `COType.PROJECT_BLUEPRINT` (and `COType.LOCAL_ADAPTATION`), requiring `structured_data.safety_boundary` to be truthy before publishing — but `schemas/structured_data.py`'s `ProjectBlueprintStructuredData` (and `LocalAdaptationStructuredData`) never defined a `safety_boundary` field. `validate_structured_data()` calls `model.model_dump(mode="json")` after validation, and Pydantic's default `extra="ignore"` silently drops any field not on the model — so even supplying `safety_boundary` in the input dict, it never survives to reach the gate that requires it. **This meant no `project_blueprint` object could ever pass this gate, seed-authored or otherwise** — a full type of content was structurally unpublishable, not just this seed pack's instances of it.

Fixed: added `safety_boundary: str` to `ProjectBlueprintStructuredData`, matching the field `SkillGuideStructuredData` already has. Authored real, per-object safety content for the 9 blueprints (generator carbon-monoxide/fire risk, electrical panel work needing a licensed electrician, asbestos/lead exposure risk in old insulation, water-testing escalation for compromised sources, mutual-aid map privacy/consent, etc.) rather than boilerplate. All 9 published after the fix. `LocalAdaptationStructuredData` has the identical latent gap — left unfixed since no objects of that type exist yet to be blocked by it; flagged in TODO.md rather than changed speculatively.

**Result**: 51/51 resilience-seed objects now published (was 2/51 as of the previous follow-up), 0 draft, 0 pending outbox events after the worker processed the new `version.published` events. Full test suite re-run after the schema change: 400 passed, 6 failed — no regressions, same known issues (see STATUS.md). Eval re-run: **5/11** (`eval/reports/2026-09-07.md`), up from 3/11. Remaining failures are exactly the two gaps already identified above (zero evidence-span citations on hand-authored content; several gold-file `expects_any` slugs — `power.starter-solar`, `water.rain-barrel`, `water.chlorine-treatment` — that don't exist under any name in the seed pack) plus the Spanish query, which is deliberately expected to keep failing until real multilingual content lands (per the gold file's own comment) — none of the three are retrieval bugs, and none should be "fixed" by gaming the eval (fabricating citations, or rewriting the gold file to match whatever exists rather than what should exist).
